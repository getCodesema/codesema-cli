## [Unreleased]

### Added

- **Normalized task recap** (`@codesema/contract` 0.6.0, decision D10): a `RecapRecord` that replaces the free-form "last turn's summary" that used to fill the MR description (`buildMrDescription`, `task-ship.ts`) with a contract calqued **literally** on `ReviewRecord` — sanitizer, JSON Schema, cross test — so a recap carries the same tolerance guarantees as a review and can be validated by the same tooling. `packages/contract/src/recap.ts` exports `RecapRecord`, `sanitizeRecap` (whitelist-and-truncate, never throws) and `recapRecordSchema` (draft 2020-12, on the pattern of `reviewRecordSchema`); `packages/cli/src/task-recap.ts` adds the **deterministic-first generator** (`generateRecap`) and `renderRecapMarkdown`. Every factual field has ONE source, decided before any code: `files[]` from the `baseline_sha..branch` diff (T1.5), `tests[]` from the persisted `checks.json` (T3.1, with `unconfigured` never shown as green and `error` always named), the cost from the task record (T1.8, copied verbatim, never recomputed — `tokens` is summed by the CLI from the turns' own counters), `branch`/`mr_url` from the ship's journal event. The model is read for **exactly three** fields — `summary`, `changes[]`, `decisions[]` — and the rejection of everything else is **structural**: the generator never looks up any other key on the model's output, so invariant 4 ("the LLM never produces a verdict, a percentage or a figure that counts") holds by construction rather than by filtering. When a source is missing (no baseline, no checks.json, no model output) the recap degrades honestly — an empty or synthetic value (the latter flagged `synthetic: true`, never left to a reader to infer from a sentence in `command`) plus a readable reason — rather than inventing one; `generateRecap` has no caller yet, so every degradation is only RETURNED (`degradations: RecapDegradation[]`), never journaled or API-surfaced from here — that is for whichever future caller wires this generator in. `criteria[]` absence is deliberately **not** treated as a degradation (DP12: it is the normal state of a task with no linked ticket). A task record with no usable branch (a hand-edited or truncated `task.json` — `sanitizeTaskRecord` guards `id` but not `branch`) is a REACHABLE case, not a hard invariant: `recap` comes back `null` with its own reason, never a fabricated identity. Stored at `.codesema/tasks/<id>/recap.json`, written atomically (`writeJsonAtomic`) and readable back only through `sanitizeRecap`, never a bare `JSON.parse` — its absence is a normal state, not an error. `renderRecapMarkdown` neutralizes every field the model or a linked ticket/review can have authored — `summary`, `changes[]`, `decisions[]`, and `criteria[].text`/`.evidence` (denormalized ticket wording and the reviewer's own quoted grounding, DP12) — before any of it reaches the page: each is collapsed to CommonMark line terminators (LF, CRLF, **and a lone CR — all three are equivalent line breaks under CommonMark**), blockquoted or escaped one line at a time, and its leading block-opening character (heading, quote, list, ordered-list marker, fence, table pipe, or a raw `<` that would open an HTML block) backslash-escaped, so a forged `## Acceptance criteria`, a fabricated file count, a fake `**Merge request:**` footer or a live `<img>`/`<!--` can never render as a live block positioned ahead of the real content. `files[]`, `tests[].command`, `branch` and `mr_url` are CLI-measured, never model-authored — but (round 4 correction: an earlier version of this entry, and of the doc comment above `renderRecapMarkdown`, framed that provenance itself as what made them "safe to render plain", which is false as a safety argument once a JSON Schema is published — `renderRecapMarkdown` must hold for every `RecapRecord` the schema admits, not only the ones this CLI's own generator happens to build) what actually makes them safe is that `sanitizeRecap` now constrains all five of `branch`, `mr_url`, `files[]`, `tests[].command` and `criteria[].text` to be **mono-line by construction** (`recap.ts`'s `line()`: every Unicode control character, not merely the three CommonMark line-terminator forms, maps to a space before the value is stored), matched by a `pattern` on each of the five in `recapRecordSchema` (round 5 correction: that pattern's negative lookahead reached with `.*`, which in ECMA-262 without the `s` flag — the way a JSON Schema `pattern` is compiled, `ajv` included — stops at U+2028/U+2029; those two are `Zl`/`Zp` and so were not in the refused `\p{Cc}` class either, which made every control character placed *behind* one invisible to the lookahead and left the **published** guarantee false even though both of this CLI's own layers scrub the value. The lookahead now reaches with `[\s\S]*` and refuses U+2028/U+2029 themselves, which `line()` already folds to a space). This normalization runs at BOTH layers: the data layer (`str()`/`line()` in `recap.ts`, and `sanitizeCriterionVerdict`'s `evidence` in `ticket.ts`) normalizes before a value is ever stored, and the render layer repeats it independently as defense in depth (`collapseToOneLine` AND `inlineCode` on all four of `files[]`/`tests[].command`/`branch`/`mr_url` — round 5 correction: the code span stopped at `files[]`, so a repo-declared checks command, the readable cause on the `synthetic` entry built from `checks.error`, and the `mr_url` read off a forge CLI's stdout each rendered **live** markdown — a remote tracking image and a phishing link in the very MR description T3.5 posts. A code span is preferred over a `<…>` autolink for `mr_url` because an autolink stays inert only while the value has no space, and `collapseToOneLine` does not remove interior ones), so a `RecapRecord` built by hand (bypassing `sanitizeRecap`) — or one built from a repo-declared string this contract does not otherwise bound (`.codesema/config.json`'s `checks.commands[]`, read by `readChecksConfig`, has no newline filter) — is neutralized just the same. `files[]` is read via the same `-c core.quotePath=false -- .` argv `prep.ts`/`preview.ts` already use, so a non-ASCII path comes back as itself rather than a quoted octal escape. Introduces the shared `CriterionVerdict` type (decision DP12) in `packages/contract/src/ticket.ts`, beside `AcceptanceCriterion`: `{ criterion_id, status: 'met' | 'unmet' | 'unclear', evidence? }`, with `sanitizeCriterionVerdict`/`sanitizeCriterionVerdicts` — an id the model invented is discarded (never reconstructed), an out-of-enum status degrades to `'unclear'` (never to `'met'`), and a repeated `criterion_id` collapses onto its first occurrence (same doctrine as `sanitizeAcceptanceCriteria`'s own dedup) — meant to be reused verbatim by the review's own per-criterion verdicts (T3.2, not yet landed) and by the recap, which additionally denormalizes the criterion's `text` since a recap reads on its own, outside any context, and applies the same dedup in `sanitizeRecapCriteria`. Every text field, including `CriterionVerdict.evidence`, is truncated in CODE POINTS (`cutCodePoints`, exported from `ticket.ts`), never UTF-16 units, so an astral character is never split into a lone surrogate. `recapRecordSchema` requires a non-blank `pattern` (round 4 correction: replacing a bare `minLength: 1`, which let a whitespace-only string like `'   '` through even though every one of these fields is trimmed before the sanitizer checks for emptiness) on every array-item string (`changes[]`, `decisions[]`, `files[]`) and on `criteria[].text`/`.evidence`, matching the sanitizer's own refusal to ever emit an empty or whitespace-only entry or optional key — `branch`, `mr_url`, `files[]`, `tests[].command` and `criteria[].text` additionally forbid any embedded control character (mono-line, see above). `tokens`/`cost_ticks` now also carry `maximum: 9007199254740991` (`Number.MAX_SAFE_INTEGER`), matching what `optionalNonNegativeInt` already silently enforced on the sanitizer side. `buildModelFields`'s degradation now reads off the SANITIZED record rather than the model's raw output, so a summary/changes/decisions that only sanitizes down to nothing (`'   '`, `'\n\n'`, blank-only bullets) is reported as a real degradation instead of `degradations: []`. `packages/web/src/types.ts` mirrors `RecapRecord` and its sub-types by hand, `synthetic` included.
- **Task resources are released instead of leaking forever.** Nothing removed a task's `codesema-home-<id>` container volume anywhere — not on ship, not on abandon, not ever — and `.codesema/tasks/`/`.codesema/worktrees/` only grew. Three independent mechanisms now close that gap, all through the same `IsolationExecFn` seam as the rest of isolation (never a runtime binary named in the ship/abandon lifecycle code): (1) a successful **ship** and an **abandon** both release the task's HOME volume, for container-isolated tasks only (nothing was ever created for a policy-isolated one); (2) a **boot sweep** removes any `codesema-home-<id>` volume whose id no task claims, across EVERY registered project. The claimed-id inventory is built from directory names on disk (`taskIdsOnDisk`), never from parsing `task.json` — a record this process cannot currently read still names a directory that exists, and a claimed id must never depend on that file being parseable at this instant. The sweep is refused outright — not run on a narrower list — the moment either the project registry itself (`projects.json`) or any registered project's task store could not be read completely, and again if the resulting inventory is empty; a second inventory is taken and re-checked immediately before EACH individual removal, closing the window between that snapshot and the runtime's own (slow) `volume ls`/`volume rm` round trips. Volumes this process creates now also carry a `codesema.workspace=<uid>` ownership label, read back at sweep time and used as an EXCLUSION only, never a gate: a volume labeled for a DIFFERENT known user is never touched — docker and podman alike, podman's `{{.Labels}}` rendering a Go map string rather than `k=v` pairs and getting its own extraction format so the exclusion actually works there too — while an unlabeled volume (pre-T1.9, which is every volume 0.12 ever created) is swept exactly like any other orphan by default, since recovering exactly those is the whole point of the sweep (design.md Décision 1: identification by NAME, never by label). Because the label is an exclusion rather than a gate, "no label" is never inferred from a field this process failed to read: the sweep asks the runtime ITSELF which volumes carry the label (`volume ls --filter label=codesema.workspace`, a second listing), so absence from that answer is a positive statement rather than a parsing artefact, a labelled line that does not have the shape it was asked for cancels the sweep instead of reading as unlabelled, and a `--version` probe that could not tell podman from docker (the probe that decides which label template to request) abstains and stops the sweep rather than guessing docker — an orphaned volume surviving to the next boot costs disk, another user's volume deleted on a guess costs their agent's home; (3) a configurable **retention** pass (`taskRetentionCount` in config, default 20 — same bound as the review archive cap) keeps the N most-recently-updated TERMINATED (shipped/failed) tasks per project untouched and fully purges the rest — worktree, HOME volume, and the task's own `.codesema/tasks/<id>/` directory — while active and `interrupted` (resumable) tasks are never candidates, whatever the count, and the branch is **never** deleted by this pass (unattended background housekeeping has no way to judge whether a branch carries work worth keeping; only the worktree is reclaimed). A directory retention could not actually remove (permissions, a lingering handle) is reported honestly rather than counted among the purged, and so is a WORKTREE it could not remove — `git worktree remove --force` is refused on a locked worktree, or on one holding a file a rootful containerized turn wrote as root, and purging the record on top of a worktree still standing would turn it into a permanent orphan no future pass could ever find; that task is skipped whole and retried on the next boot; a worktree lock stolen from a live holder, or a removal that had to proceed without it, is named on the same notice line. Retention's own worktree removal runs `git worktree remove --force`, which is destructive on uncommitted content — before it runs, retention now reads `git status --porcelain --untracked-files=all --ignore-submodules=none` on the worktree (the two flags matter: `status.showUntrackedFiles=no` and `diff.ignoreSubmodules=all` are documented, common git settings that make the plain command silent about exactly the files a failed commit leaves behind, and `-uall` also counts untracked files one by one instead of folding a directory into a single entry, so the reported count is the number of files at stake) and, when it is dirty (a turn whose commit failed — missing git identity, a rejected hook — leaves real work sitting there uncommitted), skips the purge entirely and names it instead: `task <id>: worktree kept, it carries N uncommitted change(s)` (an unreadable status is treated the same way, never guessed clean). A per-project summary line (`retention purged N task(s)`) is emitted once per boot when at least one task was actually purged. A release or a sweep that fails is never a reason a task fails to reach its terminal status, nor a reason boot fails: it is named on a new, deliberately NEUTRAL `TaskEventType` `'resource'` (`data.name` ∈ `home_volume_released | home_volume_not_released | container_runtime_absent`, mirrored in `packages/web/src/types.ts` and rendered as a plain journal line, never red — a `volume rm` that fails takes nothing and refuses nothing, so it carries no reason code, same doctrine as `cost`). The boot sweep and the retention purge are the one exception: neither writes to a task's own journal (`appendTaskEvent`'s `mkdirSync` would resurrect a purged task's directory, or race the deletion retention itself just performed), so both report only through the workspace's boot notices.
- **Grok joins the auto-detected roster** (`grok`, xAI), and with it a way to feed an agent that cannot read a stream. It is the fourth provider `detectAgents` probes, with the models the CLI itself reports (`grok-4.6`, `grok-4.5`, the mid-tier one doubling as the dual-review judge) and the four reasoning efforts it accepts (`low`, `medium`, `high`, `xhigh`). Three of its behaviours diverge from the rest of the roster, each verified by running grok 1.0.5 rather than read off a doc. **It cannot be fed on stdin**: `-p/--single` takes the prompt as an argument, and `--prompt-file` wants a real path — `/dev/stdin` does not stand in for one, because node hands a spawned child a Unix SOCKET as stdin (libuv builds stdio out of `socketpair`) and opening `/dev/stdin` on a socket fails with `ENXIO`. Passing the prompt as an argument instead would cap it at 128 KiB minus a page (`MAX_ARG_STRLEN`), a limit a real diff reaches. So `runAgent` learned a third way: a command naming **`{promptFile}`** gets the prompt written to a file in a 0700 temp dir, mode 0600 — the prompt carries the whole diff — the placeholder substituted with its quoted path, an immediately closed stdin so nothing waits on an EOF that will not come, and the file removed by name (never recursively) the moment the run settles, whatever settled it: a clean exit, a non-zero one, a watchdog cut, a Ctrl-C. Any custom agent command can use it. **Its tool list is no lock**: `--tools ""` and `--tools <unknown>` both leave every tool reachable — a review run with them read a canary file off the disk — so the review hardening uses a permission rule instead, `--deny '*'`, which refuses the shell and the file tools alike. What that rule does NOT buy is the absence of injected instructions: grok loads the repo's `AGENTS.md`/`CLAUDE.md` even with every tool denied (a planted file steered its answer) and has no equivalent of codex's `project_doc_max_bytes=0`, so the README says the boundary is execution rather than claiming a boundary that is not there. **Its `acceptEdits` writes nothing**: headless, that mode announces the edit and exits 0 having changed no byte, so the fix runner gives grok `--permission-mode auto`, the mode that actually applies one. Everything else falls out of the existing tables — `XAI_`/`GROK_` join the provider prefixes `agentEnv` keeps, every other credential in the environment is still stripped, and the dual-review judge remaps the model through the same `AgentDef` lookup as the other three. Container isolation stays claude-only and still says so.
- **The branch is the deliverable even of a run that failed** (T1.6), a doctrine now stated at the top of `packages/cli/src/task-worktree.ts`, ahead of every function that can make a branch disappear. Three concrete silences it closes: (1) a `commitTurn` that `git commit` refuses (missing identity, a failing hook) used to degrade to an `error` event with only the message — nobody was told WHERE the still-uncommitted work sits. The event now carries `record.worktree` and `record.branch` too, the original message untouched. (2) `renameTaskBranch` used to return `string | null`, collapsing five distinct refusals — a branch outside the `codesema/task-*` fork prefix, no usable name in the proposal at all, a proposal naming the branch's OWN current name (the ordinary case of an agent re-proposing its title, kept distinct from "unusable"), a branch already pushed, a plain git refusal — into the same silent `null`. It now returns a named `RenameBranchResult` (`{ renamed: true, branch }` or `{ renamed: false, reason, current }`), and `adoptBranchProposal` journals every refusal with its reason and the branch name that was kept; a cosmetic rename declining still never fails the turn. (3) `abandon()` used to decide a branch's fate from `record.created_branch ?? !record.work_on` alone — a branch this conversation forked, or locally materialized from an origin-only ref, was deleted outright, even carrying commits nobody asked to discard, and a work-on conversation's LOCAL head could be deleted the moment `origin/<branch>` had vanished between two turns (merged, renamed, cleaned up on the forge — the nominal case of a colleague's MR), which made that head the ONLY copy of whatever it carried. `abandon()` now never deletes a work-on branch, full stop, whatever `created_branch` says — the old finer rule is deferred to T1.9's configurable retention, which purges an EMPTY local head abandon no longer dares to. A new primitive, `branchHasOwnCommits` (task-worktree.ts), compares the branch's tip to its anchor — `TaskRecord.baseline_sha` (T1.5) when present, `record.base` resolved otherwise, with the fallback itself journaled (and split from a plain fallback into `baseline_sha_unresolved` when `record.base` names nothing at all — the maximal degradation, previously the one left silent) rather than silently applied — both sides compared as git OBJECTS (`^{commit}`), never as raw strings, since `baseline_sha` may be stored abbreviated and a string compare against `rev-parse`'s always-full sha would never match. The commit-carrying check now runs UNCONDITIONALLY, not only when the branch was otherwise deletable: a plain adopted work-on branch (`created_branch` absent, the most common shape of a work-on conversation) now signals a preserved branch too when it carries the user's own commits, not only a branch this conversation forked. The signal itself moved off the shared 'worktree removed, task abandoned' line onto its own event — that line's message stays byte-for-byte what it always was, never grown with extra fields — and its commit count is only ever a positive integer: a branch reset backward past its anchor still reads as "carries a commit" (the safe side of "tip differs from anchor") but never states a fabricated `0` alongside it. None of the four new journal facts (a rename refusal, a preserved branch, an anchor fallback, an unresolvable anchor) carries a `reason_code`: a `reason_code` is reserved for what qualifies a STOP a machine reads and a task can later un-say (DP14) — none of the four stops anything or is a degradation, a preserved branch being the doctrine succeeding rather than failing. They ride instead on a new neutral `TaskEventType` member, `'branch'` (`@codesema/contract` 0.6.0, mirrored in `packages/web/src/types.ts` and rendered generically by `TaskEventLine`) — deliberately NOT `'message'`, which the web conversation renders as an agent chat bubble backed by the turn's full response text and would have either duplicated the agent's last reply or never shown the branch fact at all. Each carries a stable `data.name` discriminant (`branch_rename_<reason>`, `branch_preserved`, `baseline_sha_fallback`, `baseline_sha_unresolved`), the same doctrine `costEvent` already uses for its own neutral events. A preserved branch is also signalled through a new optional `TaskActionResult.preserved_branch`, propagated verbatim by `POST /api/tasks/:id/abandon` even on the rare path where the task record itself vanished from under the call while it waited for the repo lock. Two review passes tightened this further: `hasOwnCommits` answers "was it right not to delete this branch", never "does it still exist to be pointed at" — a branch cleaned up out of band before an `abandon` ran (a stale checkout, an earlier partial abandon) used to still be named by `preserved_branch` and `branch_preserved`, so both are now gated on the ref actually existing, with a new `branch_gone` event covering the case where it doesn't. `resolveAbandonAnchor` resolves `baseline_sha` itself as a git OBJECT (`^{commit}`) rather than trusting its stored shape, so a shape-valid but nonexistent `baseline_sha` (a re-clone, a restored `.codesema/`, a hand-edited record) now emits `baseline_sha_unresolved` exactly like the base-fallback case that already covered this, instead of being silently treated as resolved. A work-on branch kept unconditionally now says so even when it carries no commit of its own, via a new `branch_untouched` event — otherwise the shared 'worktree removed, task abandoned' line was the only thing ever said about a branch this doctrine promises to always mention when it survives an abandon — and its message is worded separately from a forked branch's, since stating "carries a commit" as the REASON a work-on branch was kept would claim a causality that never holds for it. The branch-fate decision itself is now isolated in a dedicated `decideBranchFate` (task-runner.ts), keeping `abandon()`'s own growth in check as these cases were added.
- **Reason codes** (`@codesema/contract` 0.6.0, decision D2): a closed, shared vocabulary for every degradation codesema reports, so CLI and web stop reading free-form strings. `REASON_CODES` is a frozen table of ten codes — `checks_failed`, `review_blocked`, `criteria_unmet`, `merge_conflict`, `branch_diverged`, `agent_error`, `inactivity_timeout`, `interrupted_by_user`, `resource_busy`, `forge_unreachable` — each carrying `terminal: boolean`, the answer to "does waiting change anything?": the five terminal ones need the WORK on the branch to change (a red check, a blocking review, an unmet criterion, a conflict, a branch left behind), the five retryable ones need the RUN or its environment to change (a crashed agent, a watchdog cut, a human stopping the task, a busy resource, an unreachable forge). The table is extensible and never renamed: a test locks every code by name, so adding an eleventh passes and renaming one breaks. Alongside it: `sanitizeReasonCode` (whitelist, `null` on anything unknown, never throws), `isTerminalReason`, and `TaskReason = { code, detail? }` whose `detail` is bounded to 2 000 characters so a reason always fits a flat event payload or an HTTP body.
- **Semantic watchdog on agent runs** (decision D3). The only thing that used to stop a task's agent was `timeoutMs`, a wall clock — the one measurement that says nothing about whether the agent is alive. It fails twice over: it kills a long but working task at 15 minutes, and it lets a task that died in its first minute rot until the ceiling. `runAgent` now measures **life** instead of duration, from two signals read out of the agent's own stream: `lastActivityAt`, refreshed by every decoded frame (and by any byte a non-decodable provider produces), and `inFlightTools`, incremented on the `tool_use` blocks of a **complete** `assistant` frame and decremented on the `tool_result` blocks of a **complete** `user` frame — never on partial `stream_event`s, so each tool is counted exactly once. The inactivity count is **suspended while a tool is in flight**: an agent waiting on a twenty-minute test suite is not dead, it is waiting. A second budget bounds that wait. An orphan `tool_result` (truncated stream, replayed turn) is **ignored** and the counter never goes below zero — a negative count would look like a tool forever in flight and would disarm the watchdog in silence, which is the costliest way this can fail. Three budgets, configured in seconds, with D3's defaults: `watchdogInactivitySeconds` (30 min), `watchdogToolBudgetSeconds` (2 h), `watchdogHeartbeatSeconds` (30 s). They are read once at startup and apply workspace-wide today — per-project resolution waits for the per-project configuration work, and the README says so rather than promising otherwise. The heartbeat emits a liveness frame carrying the idle time and the tools open. `timeoutMs` is kept and renamed `absoluteCapMs` on `AgentRunOptions`, documented as the last-resort ceiling under the watchdog and never as the mechanism that detects a dead run — it still rejects with its own distinct `agent.timeout`, as `agent.interrupted` and `agent.exitCode` still reject with theirs.
- **The kill now actually kills, without losing the end of the stream.** `killGroup` sent a single `SIGTERM` to the process group and hoped: an agent that ignores `SIGTERM` survived its own kill. The escalation is now ordered and every step is bounded — close stdin, `SIGTERM` to the whole group, a bounded 5 s wait, `SIGKILL`, and **only then** close stdout, followed by a last bounded wait after which the run reports what killed it whether or not the child ever announced its death. stdout comes after the `SIGKILL` on purpose: closing it any earlier truncates the stream and throws away the agent's final words, which are exactly what says why it died. The final settle exists because no signal is a guarantee (uninterruptible I/O, a grandchild holding an inherited pipe open) and this promise is what the graceful shutdown awaits — a run that can never settle would turn Ctrl-C into a hang. Closing stdin stays the first step even though it is a no-op in today's flow (the prompt is written and stdin ended as soon as the run starts): the order is the contract, and EOF is the gentlest way to ask an agent to leave the day a caller keeps stdin open. The `detached` process group that makes one signal reach the shell *and* its children is unchanged, as is the stdin `EPIPE` guard that keeps a crashed agent from taking the host process down.
- **The caged turn is watched exactly like the host one.** Container isolation is the DEFAULT path wherever a container runtime exists, and `spawnContainer` had no watchdog at all — the fix would have missed the majority of real runs. It now arms the same budgets, the same injected clock and the same heartbeat, with the escalation the cage requires: close stdin → kill the **container by name** (killing the client alone leaves the agent running inside its box) → bounded wait → `SIGTERM` the client → bounded wait → `SIGKILL` → close stdout → bounded wait → settle anyway.
- **A watchdog cut leaves the conversation resumable.** `inactivity_timeout` is retryable in D2 — what has to change is the run or its environment, never the work on the branch — so a task the watchdog stops lands on `interrupted` (which both **Resume** and a reply accept) rather than on the terminal `failed`, carrying the code on the record and on its journal event, with a message distinct from a human Stop. Its worktree, branch and commits are kept (T1.6), so **Resume** re-runs the very turn that was cut instead of costing the user the work. A cut that a human then interrupts mid-kill keeps the watchdog's cause: the person is reacting to the stop, not causing it.
- **The absolute ceiling can no longer cancel the watchdog.** The shipped default was a 900 s ceiling (`timeout`) under a 1 800 s inactivity budget: the watchdog could never tick once, every live task still died of the wall clock at 15 minutes, and every dead one still went unnamed. Agent TURNS now derive their ceiling with `effectiveAbsoluteCapMs` — raised, never lowered, to sit above the largest budget plus the whole kill escalation — while `codesema review` and the fix runner keep their historical `--timeout` verbatim. `timeout` also gets the same guard as the watchdog keys (a whole number of seconds, at least one): now that nothing else watches the wall clock, a `0` would have read as "kill on sight".
- **A liveness stamp the UI can actually read**: `TaskRecord.heartbeat_at` (optional, absence claims nothing) is refreshed on disk and broadcast at every heartbeat period of a running turn. It is what tells a task deep inside a forty-minute tool call from one whose agent has died — `updated_at` only moves when something happens, and is deliberately left alone by a beat so the activity sort is not reordered by a task that is merely breathing. Not a journal line: a beat every 30 s would grow `events.jsonl` without ever saying anything new.
- **Cost in whole integers, with its provenance** (`@codesema/contract` 0.6.0): a turn and its task now carry what they cost, and — inseparably — **where the figure comes from**. The unit is posed once and for good: `cost_ticks`, **1 tick = 1e-10 USD** (`TICKS_PER_USD`), a non-negative integer and never a float (a float makes sums non-associative and comparisons unstable, which a running total of turns cannot survive; 1e-10 USD is fine enough that the shortest billable turn does not round to nothing). The unit is a schema choice that cannot be renegotiated once records are written, which is why it is posed before there is any data to migrate. Next to it, `cost_basis: 'harness' | 'lower_bound'` says which of two very different numbers this is, and on the record `cost_turns` says **how many turns the total covers**. **Absence means UNKNOWN, and unknown is not `0`**: a record written by 0.12 carries no cost, and neither does a turn nothing could price — the sanitizers preserve that absence instead of degrading it to a zero that would read as "this was free". A basis nobody can name drops the key rather than being guessed, and neither the basis nor the coverage ever outlives the figure it describes. `TaskRecord.version` stays `1`; all three fields are mirrored into the web types with the same comments, and nothing in the UI renders a cost it does not have.
- **Where the nominal figure comes from, and what it is not.** The cost of a turn is resolved by a new `packages/cli/src/cost.ts` through ONE deterministic order of authority, so exactly one branch ever wins. (1) **Partner-operated platform** — `CLAUDE_CODE_USE_BEDROCK` / `CLAUDE_CODE_USE_VERTEX` in the run's environment, or a model id of partner shape (`us.anthropic.…`, `-v1:0`, `@20251101`): **no cost at all**, not even the harness's, because Bedrock and Google Cloud invoice their own price lists and a number from the wrong list is worse than no number. "The run's environment" is the one the process that actually executes will see: on the host, what `agentEnv` hands the subprocess; **inside the container cage, only what the cage forwards by name**, which is neither of those switches. A host shell that exports one for some other tool therefore no longer strips the cost off every caged turn while the agent inside bills first-party — the model-shape signal, which travels on the stream itself, covers both paths and is what catches a real Bedrock or Vertex run. (2) **The agent harness's own estimate**, read from a `success` result frame: each model's cost is rounded to ticks on its own and the INTEGERS are summed (rounding once per model, never adding floats and rounding the drift at the end), falling back to the run total when no per-model breakdown is there. This is the **nominal** figure because it is the only one that covers output tokens and subagents — and it is an **estimate computed from a table bundled in that harness**, never an invoice, which is exactly what `cost_basis: 'harness'` says. Two subtypes are read: `success`, and `error_max_budget_usd`, whose `total_cost_usd` and `modelUsage` are documented as INCLUDING the response that crossed the budget. Every other error subtype is refused — a crashed run zeroes its cost fields, and a `0` from a frame like that means UNKNOWN, never free. One unusable entry voids the whole per-model map (a partial sum is a wrong figure, not a smaller one) and the complete `total_cost_usd` on the same frame is used instead. (3) Otherwise the **fallback lower bound** below. (4) Nothing usable: no figure, and a named journal line saying why.
- **The fallback table is a structural lower bound, and says so.** It bills base input, cache reads and cache writes (5-minute and 1-hour read from `cache_creation.ephemeral_*_input_tokens`, at the published 0.1x / 1.25x / 2x multipliers of base input), deduplicated **by `message.id`** — Claude Code emits one assistant frame per content block, all repeating the same usage for the same API response, and counting frames instead of responses inflates a turn several-fold. It has **no output rate at all**, on purpose: per-frame `output_tokens` is a documented placeholder, so output cannot be billed even by accident. **Subagent frames are filtered out** by their `parent_tool_use_id` before they ever reach the table — the same frames the official cost-tracking guide skips — so "subagents excluded" is a filter that exists rather than an assumption about the stream. Every omitted line item is positive, so the real bill is this figure OR MORE — `cost_basis: 'lower_bound'`. Rates are whole **cents per million tokens** (an exact integer for every published price, so the table holds no float) and carry optional validity windows selected by the **turn's own `started_at`**, never by "now": an expired rate with no successor produces no figure and a `cost_price_expired` line, rather than a stale price in silence, and a turn with no readable start date says exactly that instead of blaming a model that is in fact in the table. There is no clock anywhere on this path: a missing stamp prices nothing rather than quietly billing the turn at today's rate. The arithmetic is integer end to end; the single float→integer step of the module is one guarded `usdToTicks`, used only for the harness's USD amounts. A property test over 1 000 draws rebuilds the expected total in BigInt from independently transcribed rates — verified by mutation to fail if a rate moves, if the deduplication goes, or if anything fractional escapes.
- **Degradations are neutral, named, and say the real cause.** A cost that cannot be established is a gap in the accounting, not a failure of the work, so it rides on a new **neutral** `cost` journal event (never `error`, which would cry wolf on every turn run against a model this build cannot price) with a distinct name per cause: `cost_partner_platform_unpriced`, `cost_model_unpriced`, `cost_price_expired`, `cost_turn_undated`, `cost_counters_unusable`, `cost_harness_amount_unusable`, `cost_turn_unrepresentable`, `cost_total_unrepresentable`, and the informative `cost_drift` — a structural cross-check raised when the lower bound exceeds the harness figure, which it cannot legitimately do (the harness's figure still stands; the line is never blocking). One line per distinct subject, not one per frame, and the name is ADDED to the readable message, never replacing it. A turn **killed, timed out or crashed keeps what it had already spent**: the meter's last figure is written on the turn with its basis, because reporting a cut turn as free is the one thing this field must never do. The same fold applies when `resume` re-runs that very turn — an attempt that measured nothing erases nothing, and an attempt that measured something **adds** to what is there, since the turn really did burn both and the harness reports each run independently (it provides no session-level total, so a resumed run's figure never contains the killed one's); the provenance drops to `lower_bound` as soon as either part is one. One attempt's measurement is folded **at most once**, whichever way the attempt exits: `finishTurn` folds and then goes on to commit, emit and persist, any of which can throw and send the same attempt into the failure path, which would otherwise count it twice. The task total is **derived, never incremented** — recomputed from the turns at every turn's end, so it can only equal their sum — and it is `'harness'` only when EVERY covered turn is: a sum is never more authoritative than its weakest term. Figure and provenance are **one fact in two keys** and the sanitizers keep them together in both directions — half of it is dropped whole, because a figure nobody can interpret is worse than none and a half-kept pair makes two readers disagree about whether a turn carries a cost at all (which is how a re-run would silently replace a figure it should have added to); the record's total is the same all-or-nothing trio with its coverage. The coverage never claims more turns than a record keeps — the producer computes it from the turns it holds, and the sanitizer holds the same claim against a hand-edited file by bounding it to `[1, turns kept]` — and a sum that would leave the exact integer range is reported as such — at the turn, where the figure it could not absorb is named, and at the record, instead of vanishing into what would look like an unpriced task. Out of scope on purpose: cost display, budgets and quotas, and the cost of reviews and checks (the field exists; feeding it beyond agent turns comes with the consumers that need it).
- **Turn token counts stop triple-counting.** `TaskTurn.tokens` — and the live `task_meta` figure the workspace shows — were summed frame by frame, but Claude Code emits one assistant frame per content block and every one of them repeats the same `usage` for the same API response. A turn that used three tools in one response counted that response three times. The counter now deduplicates by `message.id`, like the cost meter does, so the same run reports a **noticeably smaller and finally correct** number: expect roughly a threefold drop on tool-heavy turns, which is a correction and not a regression. Subagent frames stay counted here on purpose — those tokens were burned by the turn, and `tokens` has always meant "what this turn burned"; only the *price* of them is a separate question, answered by the cost basis above.
- **Ticket contract** (`@codesema/contract` 0.6.0, decision D6): the format of a ticket and the extraction of its acceptance criteria are frozen once, in `ticket.ts`. A `TicketBody` is five sections identified by their English headings **verbatim** — `**Context**`, `**Goal**`, `**Scope**`, `**Acceptance criteria**`, `**Out of scope**` — the last of which is never prose: `**Acceptance criteria**` is a structured list of `AcceptanceCriterion = { id, text }`. The `id` is derived from the criterion's **text** (whitespace collapsed, trimmed, **Unicode NFC**, then FNV-1a over the UTF-8 bytes, low 48 bits, `ac-<12 hex>`), never from its position: inserting a criterion at the top of the list renames none of the others, where a positional `[C1]`, `[C2]`… numbering would have shifted every one of them and silently invalidated every verdict already emitted against them. The bounds are exported and part of the contract: `TICKET_SECTION_MAX` (4 000 characters per prose section), `TICKET_CRITERION_TEXT_MAX` (500), `TICKET_CRITERIA_MAX` (32 entries) and `TICKET_CRITERIA_MIN` (3 entries). The two **length** bounds are counted in **code points**, the way the published JSON Schema counts them, so a criterion written in emoji is bounded by what it says rather than by how UTF-16 happens to store it; a value cut at one of them is always left well formed and re-trimmed, so what the sanitizer stores is what it produces again when it reads it back. The single exception is `formatTicketProblems`, bounded in code **units** — that is the unit of the channels a refusal has to fit (a reason's `detail`, a flat journal payload), and a reason must reach them without being cut a second time — though never through the middle of a surrogate pair. The ticket's title is not in the body — it stays `TaskRecord.title`, the field that already has an identity. Every step of that derivation is **frozen**, the NFC normalization as much as the hash: the same accented sentence typed decomposed and pasted back composed is one criterion, not two, and `ticket.test.ts` pins the concrete id of concrete texts so a change to any step breaks a test instead of silently renaming every criterion already written.
- `lintTicketBody(raw)` → `{ ok: true, body } | { ok: false, problems }` is the **deterministic** gate on a ticket about to be launched: five sections present and non-empty, at least three acceptance criteria, and the **EARS** phrasing `WHEN … THE SYSTEM SHALL …` (uppercase keywords, exported as `EARS_TRIGGER`/`EARS_RESPONSE`). No model, no heuristic, no clock — the same markdown always yields the same verdict and the same `problems`, in the same order: sections in their canonical order first, then the criteria in list order. Every problem **names** what is wrong (the missing section, the minimum of three, the offending criterion, the bound it exceeds) and carries one of eleven codes — `body_not_text`, `section_missing`, `section_duplicated`, `section_empty`, `section_too_long`, `criteria_not_a_list`, `criteria_too_few`, `criteria_too_many`, `criteria_duplicated`, `criterion_not_ears`, `criterion_too_long` — added to the readable message, never replacing it, and rendered as one refusal reason by `formatTicketProblems`, bounded to `TICKET_PROBLEMS_TEXT_MAX` (2 000, the same bound a reason's `detail` and a flat journal payload already impose) with a visible `…` rather than silently clipped by whoever stores it. The `**Acceptance criteria**` section is a list and **only** a list: prose after the list, a paragraph between two lists or an introduction before the first item is refused by name (`criteria_not_a_list`) instead of being absorbed into the neighbouring criterion — absorbed prose would change that criterion's text, hence its id, hence the identity a verdict was keyed on, while the lint answered `ok`. A nested sub-bullet **belongs to** the criterion above it (its text is appended) rather than being promoted into a criterion of its own — nesting being measured against the level of the **list**, fixed by its first item, so that one bullet typed a space out of line stays a sibling with its own id instead of swallowing every criterion after it into one. An empty bullet is refused by name rather than skipped. Indentation is measured in **columns**, a tab advancing to the next multiple of four as CommonMark defines it, so a list mixing tabs and spaces is read the way every renderer displays it rather than folding siblings into one another. The body is **dedented** before it is read — the indentation common to every non-blank line removed — so a ticket pasted out of a quoted block or written inside a numbered list item is read at the margin like any other. That dedent is rounded down to a **tab stop**, which is what lets a tab be measured and a line be rewritten without the two disagreeing: no tab can then straddle the boundary, so the dedent is a pure consumption of leading whitespace and `indent(line) - base` is exactly the column the line ends up at. Without that alignment a surviving tab re-anchors at column 0 and re-expands, two indentations reaching the same column drift apart, and criteria written at one level get folded into one another — silently, with `ok` as the verdict. What the tab stop cannot take off — nought to three columns — every measurement then takes off for itself: a line's indent is read **relative to the margin of its own body**, and so is the text and the length of a section. The whole family of indentation defects reduces to one property, and that property is what the tests assert by sweep: **writing a body at another margin changes nothing it answers** — not its verdict, not its criterion ids, not a single length it announces. Indentation is **measured** to decide anything, never rewritten to decide it: a Makefile recipe or a tab-indented sample quoted in a fenced block comes back with its tabs intact, two samples indented differently stay two different samples, and a section's length is counted on the characters the author wrote rather than on the columns a tab happens to occupy. A tab is rewritten in exactly one case, and never where the parser can see it: one straddling the margin itself, in the text a section stores, becomes the columns it still owed — the resolution CommonMark gives a partially consumed tab. The parser tracks fenced code blocks (` ``` ` and `~~~`), and reads neither a fence nor a heading indented by four columns **relative to the body**, that being an indented code block: a ticket whose `**Context**` quotes the ticket template is not read as one carrying a second `**Goal**`, and a quoted code sample cannot conjure a section nor swallow the rest of the body. Inside the criteria section a fenced sample is named at any indent, since a list of criteria has no prose for it to belong to. Per D6 the lint applies to the ticket **launched** (admission on the CLI side), never to the one a human is typing in a browser: a draft is refused nothing, and a refused launch says why so its author, human or agent, can fix the body and retry. The admission point itself is wired by the task-from-issue path, in its own ticket; nothing here runs implicitly.
- `lintCriteria(list)` applies the criteria half of those rules — the minimum of three, the ceiling, the text bound, EARS, duplicates — to a **bare list**, for the route that revises the criteria of an existing task without resubmitting a whole body. Entries may be bare strings or the structured `{ text }` form, a list and the same list inside a body produce the very same `problems`, and anything that is not a list is refused with its own code. An entry carrying no readable text is refused **by name and position** rather than filtered out: dropping it first would let five entries, two of them unreadable, pass as a conforming list of three — a verdict on a list the caller never sent.
- `sanitizeTicketBody` and `extractAcceptanceCriteria` are the tolerant read-back side, same doctrine as `sanitizeTaskRecord`: whitelist and truncate, **never throw**. A non-object (a string, an array, a number, `null`) is rejected by the return value; unknown fields are dropped, missing sections become empty strings, over-long sections are truncated to the bound, criteria past the ceiling are cut, and duplicates collapse onto their first occurrence. A criterion's `id` is always **recomputed** from its text, so a stale or hand-edited one is replaced rather than trusted, and a bare string is accepted where the structured form is expected. The sanitizer deliberately does **not** enforce the lint: a body refused at admission must stay readable next to the refusal that named it. `readAcceptanceCriteria(body)` is the accessor that tells the two failures apart — `absent` (the ticket carries no criteria, which an agent may be asked to draft) versus `unreadable` (the body, or its list, is not something this contract can read) — plus how many entries it had to drop; `extractAcceptanceCriteria` stays its terse form, for callers that do not need the distinction. A gate that read `[]` from both would pass a ticket whose criteria were corrupted as one that simply had none.
- A **JSON Schema draft 2020-12** of the ticket body is published as `ticketBodySchema` (`$id: https://codesema.com/schemas/ticket-body.json`), the second published schema of the product after `reviewRecordSchema` and the first on the task side. It accepts exactly what `sanitizeTicketBody` produces and nothing else — its bounds are the exported constants themselves, and a cross test validates the sanitizer's output against it while checking that an unknown field, a positional `C1` id, an over-long section, a duplicated criterion or a list past the ceiling are all rejected. One limit is stated rather than papered over: `uniqueItems` compares whole items, and draft 2020-12 has no way to say "unique by `id`" nor that `id` is a function of `text`, so two entries sharing an id while differing in text pass the schema. That guarantee is made on the producing side instead — `sanitizeAcceptanceCriteria` recomputes every id from its text and deduplicates on it — and it is tested there.
- **A baseline per task conversation** (`@codesema/contract` 0.6.0), so `diff baseline..branch` is exactly the agent's work. When a conversation materializes its worktree, the sha of the point it starts from — the resolved start point of a fork, the tip of the branch a work-on conversation takes over — is resolved **before** the worktree exists and recorded on the new optional `TaskRecord.baseline_sha`. No commit is created for it and nothing is written on any branch: the baseline is a fact about where the conversation began, not an artifact. The field is whitelisted as a git object name by `sanitizeTaskRecord` (anything else drops the key rather than anchoring a range on a sha nobody can resolve; `version` stays `1`) and it is **write-once per lineage**: a worktree rebuilt on the same branch keeps the anchor it had, because moving it would silently redefine what "the agent's work" means halfway through and drop the turns already committed out of every diff measured from it. A rebuild normally stays in its lineage — the conversation takes its **own branch** back, the way a work-on conversation does, since that branch is where the commits of its earlier turns live. Only when that is impossible (the branch is checked out elsewhere, or was deleted) is a fresh branch forged; that one is a new lineage, so the anchor moves with it — otherwise the base's own commits would be credited to the agent — and the change of branch is announced **whether or not** the anchor moved, naming the branch left behind and how many commits stay on it.
- The end-of-turn review is the first consumer: it measures `baseline_sha..HEAD` instead of `base...HEAD`, so a work-on conversation is no longer reviewed against the whole branch↔MR-target gap — the commits that predate it sit behind the baseline. Only the **scope** of the diff moves: the review is still titled, archived and looked up by branch and target (a raw sha there would be unreadable and would silently break incremental re-review), through a new optional `baseline` on the prep input that `computeDiffSummary` uses for the range. The empty-diff shortcut is unchanged. The baseline is used only while it holds: a record written by 0.12 that has none, a sha this worktree cannot resolve, and a sha that is no longer an ancestor of `HEAD` (a rebase) each fall back on `base...HEAD` — the exact behaviour of before — and each **say which of the three it was** in the journal instead of degrading in silence.
- **Uncommitted work is never carried into a task worktree**, and never silently: the agent starts from a committed point, and the conversation states on its first turn how many uncommitted files stayed behind in the main checkout and which commit it is starting from. Your working tree is read, never written — nothing is stashed, moved, copied or committed there. (An earlier iteration of this change did carry the dirty state over and commit it as a baseline; it was dropped because that commit rides on the branch and would publish private work-in-progress into the merge request. Carrying it over safely is deferred to its own ticket.) `TaskRecord` also gained the optional `created_branch`, true only when the conversation brought its own branch head into existence — present only when true, since "absent" is the only safe reading for whoever later decides whether a branch may be deleted.
- `worktree add` and `worktree remove` on a repo are now serialized behind a per-repository lock, `<repo>/.codesema/worktrees/.lock`, same doctrine as the global workspace lock (advisory JSON `{pid, at}`, self-healed when its holder's pid is gone) but a different scope and a different answer to contention: the global lock refuses a second workspace process, this one **waits** its turn (up to 75 s) because two worktree operations are both legitimate, they just must not write the same git index at once. The wait never blocks the event loop, so the server keeps serving while a task queues for its worktree, and it gives up at once when the human interrupts the task instead of sitting out the budget. **Age alone never makes a lock stealable**: an old lock only proves the operation behind it is slow, and a slow holder is still writing to the git index — so a live holder is waited for and then refused, never robbed. Only a holder that is gone (a dead pid, or this process's own residue) is stolen, after re-reading the lock immediately before removal and confirming it is still the very same holder — so a process that took it in between is never evicted; the narrow window between the re-read and the removal itself remains, documented in the code, with git's own index lock as the net under it. One valve survives, for pid RECYCLING only: a lock still "alive" fifteen minutes on (an order of magnitude past the 75 s budget, so no patient caller can ever reach it) is treated as the residue of a process that died with the machine and whose pid was reused — otherwise it would wedge the repository until a human deleted the file by hand. That steal is a degradation, not routine self-healing: it is reported to the caller and named on the task's journal with the dispossessed pid and the lock's age, under `resource_busy`. The lock file is also published atomically (written aside, then hard-linked into place), so no reader can ever catch it existing but empty and mistake a fresh holder for an abandoned one. A lock NAME that cannot be claimed at all (a filesystem without hard links, a directory squatting the path) fails immediately with its real cause instead of burning the whole budget to then blame a holder that never existed. A wait that runs out fails with the `resource_busy` code, the holder's pid and how long it had been holding — and, being retryable, lands the task on `interrupted` (which Resume picks back up) rather than on the terminal `failed`. That is now the general rule rather than one code's special case: a failed turn whose degradation names a **retryable** code parks the task on `interrupted` and is announced by an `interrupted` event, while a **terminal** one lands `failed` with an `error` event — the badge and the timeline never disagree, and no Resume button is offered for a door that is closed. One consequence is worth stating plainly: a work-on conversation whose materialization loses the lock now keeps its branch claimed, where the old terminal `failed` released it — starting a second conversation on that branch is refused until the first one is abandoned or shipped, which is the point of a status that can still be resumed; a removal that goes ahead unserialized rather than strand a worktree says so on the task's journal, and one that cannot happen at all is reported as a result, never thrown at an HTTP layer that does not catch. The MR/branch review runner takes the same lock around its own `worktree add`/`remove` — its worktree lives in a tmpdir but writes the same repository index — holding it only for those git operations, never for the review itself, and its cleanup acquisition is capped at two seconds and dropped outright once the workspace starts draining, so Ctrl-C never queues behind a lock.
- Abandoning a task now waits for that lock too, which makes it the one task action that spans an `await` — so it decides on the record it re-reads **after** the wait, never on the copy it read before: a ship that settled in that window keeps its `shipped` status instead of being buried under a `failed`. The two operations refuse each other in both directions (a ship in flight refuses the abandon, an abandon in flight refuses the ship), an abandon that cannot clean up leaves the task exactly where it found it — back in its queue, still startable — and a graceful shutdown waits for in-flight abandons the way it already waited for in-flight turns, so the process never exits between "worktree deleted" and "record written".
- **A rebuilt worktree goes back to the conversation's own branch** instead of forking a fresh one beside it. This was a real leak: a task whose worktree vanished (a cleaned tmpdir, a stray `rm`) used to be re-forked onto `codesema/task-…-2`, leaving every commit its earlier turns had made on a branch nothing referenced any more — out of `baseline..HEAD`, out of the review, out of the ship, and not even deleted by an abandon, which only knows the branch the record currently names. The rebuild now checks that branch back out, exactly as a work-on conversation does: same branch, same anchor, same work. Re-forking is the exception (the branch is checked out elsewhere, was deleted, or its ref survived without the commit it names), and it is announced whether or not the base moved — naming the branch left behind, and how many commits stay on it when that branch is still there to count them.
- The same rebuild also says what it **found**, not only what it left: the new optional `TaskRecord.head_sha` remembers the tip each materialization and each committing turn leaves on the branch, so a rebuild can tell "the branch is where I left it" from "somebody pushed to it while my worktree was gone". The anchor cannot answer that — a third party's commits land *after* the baseline and leave it a perfectly valid ancestor, so `baseline..HEAD` would have presented their work as the agent's, measured by the review and published by the ship. Foreign commits are now counted and named in the journal (a rewritten branch too, when the tip moved backwards), while the conversation still keeps its branch, which is where its own work is. A record written before the field has none: it never knew where it left its branch, so the rebuild makes no claim rather than inventing a comparison.
- Following from that, Resume no longer refuses a task whose worktree vanished, and the boot reconciliation no longer marks it `failed` on sight: both now judge the **branch**, not the checkout — the worktree is a view, the branch is where the commits live. A task whose branch survived stays `interrupted` and resumable; only when the branch is gone too is the work unrecoverable, and only then is the task `failed`, with the journal saying which. Abandon likewise stops deciding on the coarse "is it a work-on task" rule and uses `created_branch`: a branch the conversation brought into existence goes with it (including the local head materialized from an `origin/…` branch — origin is untouched), a branch it merely adopted never does.
- **A persisted task queue per project** (`packages/cli/src/task-queue.ts`, decision D1): the ids waiting their turn live in `<repo>/.codesema/queue.json` — ordered, each with its `enqueued_at`, at most 1 000 of them — written tmp+rename like every other codesema store. The module exposes `enqueue`, `dequeue`, `remove`, `list`, `position`, a boot `reconcile`, and the admission guard `claimActive(projectId, taskId)` that refuses a second active id for a project. Its file header states, where the code is read, WHY a plain JSON file is enough: a JSON file has no partial unique index, so the invariant rests on a couple — the workspace lock (`acquireWorkspaceLock`, one workspace process per **config directory**, a lock only ever stolen from a dead pid) guaranteeing a single writer, plus that guard, taken before any `await` exactly as the slot reservation was. The header also names what that scope does *not* cover: two workspaces run under two different `CODESEMA_CONFIG_DIR` values are two writers, and the day that becomes a supported setup D1 says to revisit the store itself rather than patch around it. A queue that has grown to its cap **refuses** the new task (`resource_busy`, 503) instead of dropping an entry and reporting a rank that was never real — and the refused task is settled on the spot (`failed`, carrying the refusal's own words) rather than left on `queued` where nothing would ever start it. A task whose worktree will not materialize (a base branch that no longer exists, say) is the other honest refusal: it keeps its place in the line, its journal gets ONE line naming the failure, and the pump steps over it so it never starves the conversations behind it — starting it again is the retry gesture (it is accepted rather than refused as “already started”), and a Stop, a Resume or the next boot also put it back in the running. An unreadable `queue.json` met while the workspace is running is rebuilt from the records on the spot, in memory: every read hands back the real line rather than the entries it happened to salvage, the reason is journaled on the tasks that line holds and printed once, and the repaired file is written by the next mutation (which keeps the bad bytes aside first) or by the next boot. A read itself never moves, rewrites or deletes the file — that is also what keeps a corrupt queue tellable from a repo that simply predates queues — and the copy is a *copy*: if the bad bytes cannot even be read (a stray `chmod`), the write is refused rather than allowed to destroy the last trace of the real order. A task is only ever taken out of the line when its record is genuinely gone: a record that merely could not be read at that instant (a burst of open file descriptors, a permission blip) keeps its rank instead of silently reappearing at the back of the queue two boots later, and whatever the boot *does* retire is named on the terminal. A corrupt or truncated `queue.json` never throws and never fails a boot: the unreadable file is moved aside as `queue.json.corrupt` before anything overwrites it, the queue is rebuilt from the task records, and the readable reason lands in the journal of every task the rebuilt queue holds, where `GET /api/tasks/:id` serves it back — including when the rebuild finds nothing to re-enqueue, in which case the loss is journaled on the project rather than swallowed. A file that exists but cannot be **opened** (permissions, an I/O error) is never mistaken for an absent one: it degrades loudly and leaves the records alone.
- `queue_position` on `GET /api/tasks` (optional field of `TaskRecord` in `@codesema/contract`, mirrored in `packages/web/src/types.ts`): the 1-based rank of a conversation in its project's line. **Derived, never persisted** — it is computed when a listing is served, so `sanitizeTaskRecord` deliberately drops any value found in a `task.json`, which could only be stale. A rank is a promise about *now*, so it is kept fresh at both ends: whenever the line moves, the server re-broadcasts every conversation still waiting with its new rank, and the browser takes the frame at its word rather than remembering the last number it saw. `POST /api/tasks/:id/reply` and `/resume` answer with the position too when the gesture left the task waiting behind another one, the way task creation already did, so the UI renders the right thing without a second round-trip. The work queue shows it as a quiet `#N` pill on each waiting card, with a title spelling out how many conversations are ahead of it in that repo.
- One broken project no longer takes the workspace down with it. A repo whose store cannot be read at boot (a `.codesema/` gone read-only, a task directory an outside tool corrupted) prints a warning naming the project and the workspace opens on all the others — where it previously threw out of `createTaskManager` and the whole command died before the server listened. Same posture on the event bus: a subscriber that throws while a task frame is broadcast is caught and skipped, so a single bad listener cannot abort a turn's persistence half-way through. And the same posture again on the store's own listing, with its other half attached: a `.codesema/tasks/` directory that will not list at all (a permission change, a burst of open descriptors) yields no records rather than throwing — and **says so, naming the project**, once per incident and again if it recurs, instead of letting a whole repo's board read as empty in silence.
- The three copies of the tmp+rename recipe (`task.json`, `checks.json`, `projects.json`) are now one shared helper, `writeFileAtomic`/`writeJsonAtomic` (`packages/cli/src/atomic-write.ts`), with a filesystem seam so a test can watch the ORDER of mkdir → write-tmp → rename and prove no reader ever sees a partial file. Behaviour is byte-for-byte what it was: two-space indent, trailing newline, same paths.
- Codes now travel with the four degradations that already existed, **added to** their readable message and never replacing it (they keep their exact wording and payload): the graceful shutdown and the interrupt button mark the task `interrupted_by_user`, a review that comes back KO marks it `review_blocked`, a task creation refused because the requested container cage is unavailable answers `resource_busy`, and a ship that pushed the branch but found no `gh`/`glab` to open the merge request reports `forge_unreachable`. The code rides in its own `reason_code` field on the journal event — never as a key inside `data`, whose payloads are untouched — and the full `{ code, detail }`, detail being the producer's own message verbatim, lands on the task record as the optional `reason`. A record or journal line written by 0.12 simply carries none, and a task that moves on (a turn restarting, a review coming back OK, a merge request finally opened) drops the reason it was carrying rather than keeping a stale claim. `POST /api/tasks` propagates the code verbatim in its refusal body, next to the message, the way it already does with `existing_task_id`.
- **Forge issues, read and write** (`packages/cli/src/forge-issues.ts` and its parsers in `packages/cli/src/forge-issues-parse.ts`, decision D5): `listIssues`, `getIssue`, `createIssue`, `commentIssue`, `closeIssue` and `setLabels`, all going through the `gh`/`glab` the user already has — porcelain first (`gh issue list|view|create|comment|close`, `glab issue list|view|create|note|close`), `gh api` / `glab api` only for what no porcelain covers. **No token is ever read, written or stored**: the authentication is whatever `gh auth` / `glab auth` already set up. Same degradation model as the merge-request client it is modelled on: every operation answers a typed success or `{available:false, reason}` and **never throws** — `no-remote` when the repo has no `origin` (and then nothing is probed at all), `no-cli` when every forge binary is missing, `cli-error` when one ran and failed. One member **diverges** from `ForgeMrsResult` on purpose: `invalid-input`, for what is refused *here* — an issue number that is not a positive integer, a title that sanitises to nothing, a label no forge could express, an argument the kernel would refuse (Linux caps a single argument at 128 KiB, one multi-byte `--body=…` away: it is checked before the spawn, and the `E2BIG` the check cannot see is caught as the net under it). Those never launched a binary, so calling them `cli-error` would have made D2 journal a `forge_unreachable` that did not happen; `forgeIssueReason()` maps them to **no code at all**, the message alone, and keeps `forge_unreachable` for the three real forge failures. The unavailability also carries an optional `detail`, the failing CLI's own words, **added** to the code and never replacing it — its own words, never the argv: a timeout says `timed out after 8s` where `execFile` would have echoed back the whole command line, and an oversized read names the buffer. Parsers validate field by field and reject the **whole** array at the first shape mismatch, so a truncated or half-typed payload becomes an honest unavailability instead of a silently amputated issue list; an issue with no description keeps its empty body rather than being thrown away, and the sanitizers take `unknown` and degrade rather than throwing on the `null` an untyped caller can always hand over. `listIssues` is never silently capped either: both CLIs stop at 30 by default, so gh is asked for one issue past the explicit cap of 200 and glab **pages** (GitLab clamps a page at 100) until a short page proves the list complete — and whichever way the walk ends, the cap is applied and a list that really is longer comes back with `truncated: true` rather than looking whole, the two forges answering the same numbers on the same repo. `detectForgeHint` still skips the obviously wrong CLI, and a self-hosted remote still tries both — for **reads**. A **write** never walks that ladder: once a CLI has actually run, its failure may hide a created issue or a posted comment, so the write stops there and reports honestly instead of replaying itself into a duplicate (a binary that is merely missing never ran, so writes do move past it). The `gh`/`glab` asymmetries are documented in the module rather than smoothed over — a `comment` on GitHub is a `note` on GitLab, `--body` there and `--message` here, `--state open|closed|all` against `--closed`/`--all`, one `--limit` against `--page`/`--per-page`, an editor and a confirmation to disarm on `glab issue create` (`--no-editor --yes`) that `gh` does not have, labels as objects against plain strings, `OPEN`/`CLOSED` against `opened`/`closed`, and `setLabels` reaching for `api` on **both** forges because neither porcelain can REPLACE a label set (only add to or remove from it). Every call is `execFile` with an explicit argv, never a shell string: user text rides an attached value (`--title=…`) so a title of `--repo attacker/evil` cannot be re-read as an option, issue ids are typed numbers, control characters are neutralised, and a label carrying a comma is refused **by name and with its reason** — the read side keeps such a label verbatim, GitLab's API cannot write it back, and a call that succeeds on one forge while mangling the set on the other would be worse than one that says no. All of it is asserted on the argv by tests that never run a forge binary and never touch the network, through the same `execFn` injection seam the rest of the repo uses.

- **Issue hierarchy, parent → child, one level** (`packages/cli/src/forge-issues.ts` and `packages/cli/src/forge-issues-parse.ts`, decision D8): `linkChildIssue`, `unlinkChildIssue` and `listChildIssues` extend the T2.1 issue client with the **greatest common denominator** of what GitHub and GitLab each offer, the two asymmetric API models kept apart rather than smoothed into one shape. GitHub goes through the sub-issues REST endpoints (`gh api …/sub_issues` to link and to list, `…/sub_issue` to unlink); the write body wants the child's internal database `id`, resolved first with one extra read, while the parent keeps riding its plain number in the URL like every other endpoint in the file. Listing is a single call at `per_page=100` — GitHub documents "up to 100 sub-issues per parent" as a **product** limit, not a pagination guarantee this endpoint enforces, so `truncated` follows the page length (a full page of exactly 100 reads as possibly truncated) rather than being hard-coded to `false`, which an earlier pass had done. GitLab goes through the GraphQL work-item hierarchy widget: the root field is `workItem(id: WorkItemID!)` (`Query.issue` has no `widgets` field at all), `workItemUpdate(input: {id, hierarchyWidget: {parentId}})` to link, the same mutation with `parentId: null` to unlink, and a `children` connection walked with a **real cursor** (`first: 100`, `after`, `pageInfo.{hasNextPage,endCursor}`) to list — GitLab silently clamps any `first` above 100 rather than refusing it, the exact silent-truncation shape already flagged once on the plain issue list; `hasNextPage: true` with no cursor to reach the next page still forces `truncated: true` rather than falling back to a length check that a short page could pass by accident. A child's URL is rebuilt from `webPath` (relative, nullable) against the parent's REST-resolved origin, never `webUrl` (not a field on this type); its description and labels live in nested `WorkItemWidgetDescription`/`WorkItemWidgetLabels` widgets, found by which key each widget carries rather than by position in the array. GraphQL cannot resolve a project-scoped issue number on its own, so BOTH ids are resolved first through the REST shortcut `setLabels` already uses (`projects/:fullpath/issues/{n}`), then rebuilt as the canonical `gid://gitlab/WorkItem/<id>` global id — not the deprecated `gid://gitlab/Issue/<id>` alias, which GitLab documents as removable without notice — one round trip GitHub's link/unlink does not pay. Unlinking is itself asymmetric and says so rather than hiding it: GitHub's `DELETE …/sub_issue` validates the (parent, child) pair through the URL and the body together and refuses a mismatch, where GitLab's `parentId: null` mutation takes no parent to confirm against and clears whatever parent the child currently has. Capability is **probed, never assumed, narrowly** (D8 decision 2): only a GraphQL top-level error whose message matches a *recognized* schema-gap signature (a `"…doesn't exist on type…"` complaint naming the hierarchy widget or one of its input types) is reported as the NAMED unavailability (`{available:false, reason:'unsupported'}`) distinct from an ordinary `cli-error`; any other top-level error — an authorization refusal, a malformed query, a business rejection nested under `data.<op>.errors` — stays an honest `cli-error`, since classifying every GraphQL error as "the edition can't do this" would permanently disguise this module's own bugs as a forge limitation, `forgeIssueReason` mapping `unsupported` to no D2 code at all. GitHub's own capability gap (an old GitHub Enterprise Server) is not given the same distinct name: a REST 404 cannot reliably tell "not found" apart from "not supported" the way a GraphQL schema error can, so it surfaces as an honest `cli-error` instead of a guessed `unsupported`. The one-level cap is enforced **against the real forge state**, and on GitHub it is the ONLY thing enforcing it: GitHub's own docs allow up to eight levels of nested sub-issues, so the forge never refuses a second level on its own. Beyond a purely local auto-reference refusal, the guard reads the parent's actual current parent (`GET …/issues/{n}/parent` on GitHub, `WorkItemWidgetHierarchy.parent` on GitLab) and the child's actual children before any write, so a fresh call sharing no process state still catches "link A→B then B→C" or "link a parent to its own child". On GitHub, "no parent" is read from that same 404 REST answer, but ONLY on the exact recognized message GitHub's API returns for a missing parent, `No parent issue found` (checked live against `api.github.com`) — a bare `404` anywhere else in an error's text (a locked-issue validation error, a proxy's HTML 404 page relayed as a 502, a rate-limit message linking a docs URL) is refused as an ordinary `cli-error` instead, fail-CLOSED rather than guessed as "no parent". A caller-supplied `child → parent` cache (seeded by `listChildIssues`, updated by link/unlink) is consulted first and, on a hit, skips the read, but is only ever an **accelerator**, never the source of truth; a non-`Map` value passed as the cache degrades to a fresh one rather than throwing. `listChildIssues` validates the forge's answer field by field, on the pattern of `parseGhMrList`/`parseGlabMrList`: the first shape mismatch rejects the whole array, never a partial one. Per DP5, none of this touches `packages/contract/src/reasons.ts`'s `REASON_CODES` table, `packages/contract/package.json`, or the web mirror: the hierarchy's unavailability is carried entirely by the client's own result union — that enum qualifies what stops a task, and a forge that cannot link a parent to a child stops nothing. Two round-4 fixes: the GitLab cursor walk's loop-exhaustion exit (hitting the page cap without ever seeing `hasNextPage: false` or a missing cursor) now still derives `truncated` from the last page's own `hasNextPage`, instead of falling back to a length check a permission-filtered empty tail page could pass by accident; and a write is now **pinned** to whichever forge the one-level guard's own reads actually verified — a guard answered by `gh` can no longer have its write fall through to `glab` on a blocked pre-write resolve, since that would write to a forge whose state the guard never checked. Round 5: the guard now refuses locally, before any write, when its two reads land on **different** forges (a `gh` read of the parent's state and a `glab` read of the child's would pin nothing usable); the pin can no longer leak past `candidatesFor` on the mirror direction either, so a guard settled on `glab` still refuses to let `gh` answer the write even if `gh` becomes reachable again by write time. The two GraphQL mutation strings (`workItemUpdate`'s `hierarchyWidget` argument, set and clear) are now exported and locked by their own test, next to the read-side query constants — a misspelling there used to present GitLab as unable to link a parent at all, indistinguishable from a real edition gap. The README's version note for this chapter is now honest both ways: `glab 1.53.0` is cited where it is actually verifiable (the GraphQL passthrough), and GitHub's REST surface explicitly carries no `gh` version, since it was checked against current REST documentation rather than one CLI build.

### Changed

- `detectTarget` now asks the forge which branch a review targets **whatever the head ref is**. It only probed `gh`/`glab` when the head ref was `HEAD`, so `--branch other-branch` skipped the forge entirely and jumped straight to `origin/HEAD` — incoherent the moment the forge is the source of truth (D7). A named branch is asked about through the **list** form, `gh pr list --head=<branch>` and `glab mr list --source-branch=<branch>` (flags verified against gh 2.46.0 and glab 1.53.0), never as a positional: `gh pr view 1234` and `glab mr view 1234` read a numeric argument as pull request **#1234**, so a branch called `1234` would have adopted the target of a completely unrelated merge request. The `HEAD` case is untouched, argv and answer alike; `target_source` now names the command actually run (`glab mr list` vs `glab mr view`); a ref that could be read as a flag skips the probe rather than reaching a CLI, and the value is attached (`--head=…`) so it cannot be re-read as an option either; the fallback order (forge, then `origin/HEAD`, then the nearest merge-base heuristic) is unchanged. `detectTarget`'s fourth parameter is now an options object, `{ headRef, execFn }`, whose `execFn` is the test seam: the forge probe is asserted on its argv, never run.
- The preview endpoints keep that new forge probe off the request path. `/api/preview` and `/api/preview/diff` resolve a branch's target on every call — one for the panel, then one per file clicked — which now means a `gh` **and** a `glab` probe (up to 8s each) per request for a branch that is not checked out. A target the forge **answered** is memoised for 30s per repo and branch (`PREVIEW_TARGET_TTL_MS`, dropped wholesale past 64 entries), so a burst of preview requests costs one probe instead of one each, and a retargeted merge request is picked up well inside a human's attention span. A probe that came back **empty** is never memoised: remembering "no merge request here" would hold a wrong review target for 30s after the forge came back, where re-asking only costs a failed spawn. `resolvePreviewRefs`, `buildPreview` and `buildFileDiff` take their dependencies as one object (`{ listMrs, execFn, now }`) instead of a bare `listMrs` — `now` being the clock the memo reads, so its expiry is a test rather than a 30s wait, and the memo belongs to one clock at a time (presenting another empties it, since timestamps from two clocks cannot be compared). The branch review path takes the same `execFn` seam (`createMrReviewRunner`), so no test in the CLI's forge surface launches a real `gh`/`glab` any more: the preview tests are hermetic again — no test in that file launches a forge binary — and one of them asserts that the second preview of a branch adds no probe at all.
- **The workspace now runs one active task per repo, and the queue survives a restart.** This is a deliberate break with 0.12, not a detail: two habits change at once.

  *"3 tasks in parallel" becomes "1 per repo, all repos at once."* Until now a single global budget (`maxParallelTasks`, default 3) capped running tasks across every registered project: two projects could block each other, and two conversations of the SAME repo could run at the same time — nothing anywhere guaranteed otherwise, even though a repo is exactly what two agents must not share. Admission is now decided per project: each repo runs one task and queues the rest, and projects advance side by side. Register three repos and all three can be working; ask two things of the same repo and the second waits its turn, with `#N` on its card and, on the record, the reason it waits (`resource_busy`, "another task of this project is already active", from the D2 vocabulary). A repo's turn is held until the **end-of-turn review** has given its verdict, not until the agent stops talking: the review runs another agent on the same branch, so letting the next conversation start during it would put two agents back on one repo through the side door. In practice the next task starts a little later than it did in 0.12 — after `review_ok`/`review_ko` rather than at the agent's last word. A Ctrl-C during a review stops that review's agent like any other (it now receives the shutdown signal all the way down to its subprocess) and leaves its conversation `interrupted` rather than on a verdict nobody produced; the shutdown says out loud what it is waiting for when it takes more than a moment, and gives up after 30 seconds rather than hold a Ctrl-C behind something that takes no signal (an auto-ship pushing to a remote that is not answering). `TaskSlotPool`, `createTaskSlotPool` and `DEFAULT_MAX_PARALLEL_TASKS` still exist and `maxParallelTasks` is still parsed, but none of them governs admission any more. A key that no longer does anything is a key that lies, so a config that still sets it gets one line at boot saying so; turning it into a real machine-load cap is a separate change.

  *"The queue dies with the process" becomes "the queue is on disk."* The waiting list was a `string[]` in a closure. A Ctrl-C therefore had to mark every queued task `interrupted {reason:'shutdown'}` — a turn that had never started, demoted to something needing a human gesture — because nothing would have re-enqueued it. The list now lives in `<repo>/.codesema/queue.json`, so a shutdown leaves queued tasks exactly `queued`, touches neither their status nor their journal, and the next boot re-hydrates the file and reconciles it with the records (a terminal or vanished id is dropped, a `queued` record missing from the file joins the end). Restarting the line is an explicit, ordered last step of the boot (`manager.startPending()`), not a side effect of building the manager: it happens once the server listens and the shutdown handlers are installed — so a turn that starts can be watched and can be stopped — and it prints, project by project, how many conversations it just picked back up. Only the turns that were genuinely IN FLIGHT still become `interrupted`, with `interrupted_by_user` and the same `{reason:'shutdown'}` payload as before, and they still restart only on a human Resume.

  **Nothing is asked of a 0.12 workspace, and nothing starts behind your back.** A 0.12 store has no `queue.json` at all, and an absent file is read as exactly that — no queue — never as "rebuild one from whatever looks queued". So a `queued` record inherited from 0.12 is **not** started on the first 0.13 boot: it is marked `interrupted` (`interrupted_by_user`, "orphaned by an earlier session: nothing was queued to start it") and lands in the "Needs you" zone, where one click on Resume runs it. That is the same rule the rest of the workspace already follows — an agent that writes code and commits never starts unattended on a boot — applied to a status whose only proof of intent, the queue file, does not exist. From then on the file is the truth: 0.13 shutdowns leave their queued tasks `queued`, and the next boot resumes them. Records written by 0.12 — including `interrupted {reason:'shutdown'}` ones with an unanswered turn — stay resumable through `POST /api/tasks/:id/resume` with no schema change: no field is removed from `TaskRecord` and `version` stays `1`.

## [0.12.1] - unreleased

### Changed

- Appending to a task's event journal costs a write, not a re-read. `appendTaskEvent` used to reload the whole `events.jsonl` to compute the next `seq` (and read it a second time to check for a crash-truncated tail), which made an append O(journal size) and a chatty turn — thousands of `tool_use`/`tool_result` lines — quadratic. The store now keeps the last `seq` per task in memory, filled by **one** tolerant read at first access: 10 000 appends went from 20 000 journal reads and ~23 s to a single read and ~0.1 s. Nothing about the journal's tolerance changed: the initial `seq` is still the highest **valid** `seq` on disk (illegible lines are ignored, never a throw), a crash-truncated tail line is still closed with a `\n` prefix so only the corrupt line is sacrificed, and after a restart the counter resumes from disk instead of from 0 — the in-memory cursor is dropped and re-derived whenever the file's size no longer matches what this process left, so an outside append or a hand edit degrades to a re-read rather than to a corrupt journal. `readTaskEvents(cwd, id, { afterSeq })` is unchanged and still exact.

The per-probe timeout is unchanged (8 s), the gitlab-before-github preference is unchanged, the origin-based hint still skips an irrelevant forge probe, and detected agents keep their declared order. A wait is never silent: past 400 ms the boot prints which probes it is still waiting for (both catalogs).

## [0.12.0] - 2026-08-18

### Added

- **Local agentic workspace** (`codesema workspace`, now also what a bare interactive `codesema` opens): a web UI where you hand tasks in natural language to the agent CLI you already use. Each task lives in its own conversation and works in an isolated git worktree (`.codesema/worktrees/<task-id>/`) on the branch that conversation owns; up to 3 tasks run in parallel (`maxParallelTasks` config), extra ones queue FIFO. The agent never commits — the runner commits the worktree at the end of each turn. A turn ends in a result or in a question (`waiting_for_you`; your reply starts the next turn, resuming the Claude session via `--resume`, transcript replay for other providers). Every finished turn passes an automatic local review on the task's branch (`reviewing` → `review_ok`/`review_ko`), with the repo's checks running in a sandbox alongside it, before **Ship** pushes the branch and opens the MR via `gh`/`glab`; per-task auto-ship chains a green review into a ship without a click. Reviewing a branch already checked out elsewhere (the current branch included) uses a detached disposable worktree (`git worktree add --detach`) instead of failing on git's "already checked out" restriction.
- Deterministic (no agent) preview in the MR/branch detail panel: source and target branches, commit list, changed files with +/- and status, and a per-file diff on click, rendered with the same annotated diff view as a finished review. New `GET /api/preview?source=mr&number=N` (`?source=branch&name=X`) returning branch/target/commits/files/diffStats without the full diff, and `GET /api/preview/diff?source=...&path=<file>` returning one file's diff, capped in size and truncated past the cap. The pure git computation behind `codesema prep` (target detection, commits, files, diff) is extracted into `computePrepInput`/`computeDiffSummary` (no disk writes), reused by both `prep` and the preview endpoints.
- `GET /api/mrs`, `GET /api/branches`, `GET /api/preview` and `GET /api/preview/diff` accept an optional `?project=<id>` query param to operate on a registered project's repo (unknown project → 404); without it they keep reading the launch directory as before.
- **Per-task container isolation** (`isolation` config, `auto` by default): the whole task runs in its own box instead of on your machine. The base image is resolved from the repo's `.devcontainer/devcontainer.json` or `.devcontainer.json` (parsed as JSONC, ignored when it needs compose, features or a build context outside itself), else from the checks detection, else `node:26`; a derived image adding a non-root user matching your uid/gid, `git` (probed first, then installed with whichever of `apt-get`, `apk`, `microdnf`, `dnf`, `yum`, `zypper` or `pacman` the base ships — a base with none fails the build saying so, rather than caging an agent that cannot read its own worktree) and the Claude Code CLI is built once with an empty build context and cached under a `codesema-agent:<hash>` tag keyed by the base, the whole generated recipe and the agent version. A turn then runs with the worktree as its only writable host mount (`/work`), the repo's git directory mounted **read-only** at `/gitcommon` with a generated pointer over `/work/.git` — a task worktree is a linked `git worktree`, so without it every `git status`, `diff` or `log` inside the box dies on a host path it cannot see — and `safe.directory` passed as `GIT_CONFIG_*` (command scope, per run) so a uid mismatch never turns into `detected dubious ownership`, a per-task `codesema-home-<task-id>` volume as `$HOME` (credentials seeded once over stdin, never in argv, so the Claude session survives across turns), on an `--internal` network whose only way out is a squid proxy that accepts `CONNECT` to the allowlisted domains and nothing else (`api.anthropic.com` and `platform.claude.com` by default, replaceable with `isolationAllowedDomains`), plus `--cpus 2 --memory 4g --security-opt no-new-privileges` and provider variables forwarded by name only. Inside the cage the agent gets its full tool set (`--dangerously-skip-permissions`) — the box is the guarantee. Commits stay host-side (git credentials never enter the container, and the git directory the box sees is read-only: it can read every ref and object, it cannot write one), and the automatic review and the checks stay independent counter-verification outside it. The mode is probed once at boot and recorded per task as `container` or `policy`, and a fallback is never silent: the CLI prints which mode is active and why, the task journal carries an `isolation` event, `GET /api/projects` exposes `{ isolation_available, isolation_default, isolation_reason, isolation_configured }`, and the UI shows a shield badge plus an upgrade banner. `isolation: 'container'` makes the cage mandatory (task creation answers 409 when it is unavailable), `isolation: 'policy'` always runs on the host, and only `claude` is caged today (any other agent falls back to policy, with the reason stated). Docker and podman both work, rootless podman included (`--userns=keep-id`, dedicated egress bridge instead of the pasta default). Interrupting a task kills its container, not just the client.
- **Sandboxed checks**: after every turn that commits, the repo's typecheck/tests/lint run in an ephemeral container on the task's worktree — in parallel with the automatic review, never blocking it, never able to fail the task. Plan resolution is `checks` config > declarations > lockfile: an explicit `checks` key in `.codesema/config.json` (`image`, `install`, `commands`, `network`, `timeoutSeconds`) replaces detection outright; otherwise the stack comes from the lockfile (`bun.lock`/`bun.lockb` → `oven/bun:1`, `package-lock.json`/`yarn.lock` → `node:26`, a `pyproject.toml` mentioning pytest → `python:3.12`) with the `typecheck`/`test`/`lint` scripts the repo actually declares, and the command list is then replaced by what the repo already declares to its own tooling — lefthook's `pre-push` then `pre-commit` (`lefthook.yml`, `lefthook.yaml`, `.lefthook.yml`, `.lefthook.yaml`) first, else the `run:` lines of GitHub workflow jobs whose id or name matches test/lint/typecheck/check. Declared commands go through a strict allowlist (first binary among `bun npm npx pnpm yarn node pytest cargo go make just`, no shell metacharacter, no install-like command, deduplicated, typecheck-then-test-then-lint, capped at 6). Each step is one `docker`/`podman` `run --rm -v <worktree>:/work:rw -w /work --network none --cpus 2 --memory 2g <image> sh -lc <command>` killed at `timeoutSeconds` (300 by default), with the repo's git directory mounted read-only at `/gitcommon` the same way the isolation cage does it (check commands that shell out to git — hooks, version stamps, test rigs — otherwise hit a `.git` pointing outside the mount); only the optional install step may get the network, and only when `network: true`. The run lands in `.codesema/tasks/<id>/checks.json` (per-command status, exit code, duration and output tail, plus an optional `source` naming the level that produced the commands — `config`, `lefthook`, `ci` or `scripts` — which the Checks tab shows as a "detected: lefthook" chip), streams live on the SSE `task_checks` event and a `checks` journal entry, and surfaces in the conversation's **Checks** tab (the semaphore is the tab label itself, per-command detail with foldable output, manual re-run) and as a badge on ready-to-ship cards. New `POST /api/tasks/:id/checks?project=<id>` (202; 409 while a run is in flight or when the task has not committed yet) and `GET /api/tasks/:id/checks?project=<id>`.
- **Agent-assisted checks setup, validated by a human**: when nothing is detected — or the detection is wrong — "Configure with the agent" asks your own agent CLI to *propose* a checks configuration. It runs read-only hardened (`--tools "" --strict-mcp-config --setting-sources user` for `claude`, `--sandbox read-only --ask-for-approval never` for `codex`) and reads nothing itself: codesema collects and inlines the manifests (`package.json` and its workspace manifests, `Makefile`/`justfile`/`Taskfile.yml`, `pyproject.toml`, `Cargo.toml`, `go.mod`, `.gitlab-ci.yml`, the lefthook files, the GitHub workflows, …), bounded to 4 000 characters per file and 30 000 in total, alongside a listing of the repo root. The reply must be one JSON object (`image`, `install`, `commands`, `network`, `timeoutSeconds`, `rationale`) and is sanitized before it is even displayed: an image reference that does not parse or zero surviving commands refuse the whole proposal, commands are screened against the same binary allowlist (`&&` chaining and `cd` tolerated, every other shell metacharacter refused, 8 max), the timeout is clamped to 30…3600 s and the rationale stripped of control characters. The proposal lives in memory only — a restart forgets it, and nothing reaches disk until a human clicks **Apply**, which writes the `checks` key of `.codesema/config.json` and leaves every other key of that file byte-for-byte in place. `POST /api/projects/:id/checks-setup` (202), `GET /api/projects/:id/checks-setup` (proposal state) and `POST /api/projects/:id/checks-apply` (200, 409 with nothing proposed), the two mutations under the tasks CSRF token; every state transition broadcasts on the SSE `checks_proposal` event.
- **Conversations own their branch**: `POST /api/tasks` now accepts `branch` — work *on* that existing branch directly, no derived ref, the worktree is a checkout of it — or `base`, which forks a new `codesema/task-<slug>` branch from it; the two are mutually exclusive (400), and with neither the task still forks from the detected trunk as before. Work-on tasks also take an optional `target`, the branch the MR will aim at. `origin/x` and `x` are one identity everywhere: records store the short name, existence is resolved against `refs/heads` then `refs/remotes/origin`, and a remote-only branch gets a local tracking head created for it (`git branch --track`, falling back to a plain branch). Only one active conversation may own a branch: a second one is a `409` carrying `existing_task_id`, so the UI opens the conversation that already has it instead of dead-ending, and a branch checked out in another worktree is refused with the path that holds it. Abandoning (`POST /api/tasks/:id/abandon`) removes the worktree and deletes the branch **only** when the conversation forked it — a branch you asked it to work on is never deleted — and a shipped task keeps its `shipped` status instead of being marked failed.
- Live token telemetry per turn: the agent stream's usage is accumulated as it arrives and pushed on a new `task_meta` SSE event (token meter in the conversation header, reset at each turn), then persisted on the turn record (`tokens`) when the turn ends, so a finished turn shows its own cost next to its duration and tool count.
- **Workspace project tree**: the sidebar lists the registered projects with their live counters, and the selected project expands into a tree of its open merge requests (`GET /api/mrs`) and active branches (`GET /api/branches`) with the conversations working on them nested underneath — a conversation attaches to the MR whose source branch it owns, otherwise to a node for its base branch, so derived `codesema/task-*` branches never become nodes and are filtered out of the flat "Branches (n)" list under the tree. Nodes are ordered by their most recent conversation activity and unfold by default while something is still moving. Clicking a branch opens the conversation that already owns it, or drafts a new work-on conversation on it with the MR's target prefilled — and warns, with a one-click switch to fork-from, when the branch is `main`, `master` or `develop`.
- **The agent names its own branch**: on its first turn a forked conversation is asked to open its reply with `BRANCH: <2-5 word kebab-case name>`, and the runner renames `codesema/task-<slugged title>` to `codesema/task-<that name>` before the commit, the review and the ship — so the MR source branch reads `codesema/task-update-workspace-docs` instead of `codesema/task-les-docs-sont-a-jours`. The proposal is slugged like any branch name and collisions take the usual `-2` suffix; a missing, unusable or refused proposal silently keeps the generated name. Never asked for and never applied on a work-on conversation (that branch is yours), and never on a branch already pushed.
- **Resuming an interrupted conversation**: a Ctrl-C, a crash or a `Stop` leaves the conversation `interrupted` with its worktree intact, and the next boot offers it back instead of filing it away. Interrupted conversations moved out of the folded "Done" pile into "Needs you" — nothing re-enqueues them, only a human gesture does, and that is exactly what that zone means — where a **Resume** button restarts the turn that died: same instruction, same turn (no extra turn is appended), the Claude session resumed via `--resume` when the record kept one and the transcript replayed otherwise. New `POST /api/tasks/:id/resume?project=<id>`, body-less because the instruction is already on the record, refused with a 409 when the conversation is not interrupted, when its last turn had already answered (nothing to redo — the composer is then the way forward, and the UI says so instead of showing a dead button) or when its worktree is gone. Restarting is never automatic: agents that write code and commit do not restart unattended on a boot, so the offer is a badge, a card button and the existing terminal line. A boot that finds an interrupted conversation whose worktree has vanished marks it `failed` with an `error` journal line rather than offering a Resume that would fork a fresh branch and strand its commits.
- **Redesigned workspace UI**: one dark theme (`#0a0d10` ground, `#46b17b` green, `#d9a441` amber, a deliberately blue focus ring so focus is never read as a status) with Instrument Sans and JetBrains Mono vendored in the tarball — no CDN, nothing fetched at page load. The projects rail sits on the left, a **work queue** in the middle groups conversations into "Needs you" (`waiting_for_you`, `review_ko`, `interrupted`), "In progress" (`running`, `reviewing`, `queued`), "Ready to ship" (`review_ok`) and a foldable "Done" pile (`shipped`, `failed`), and the right side is a **focus deck** of up to 3 conversations side by side: pin one (📌) and the next conversation you open replaces the loose column instead of the ones you kept. Each conversation has **Conversation** / **Diff · n files** / **Checks** tabs, a header bell counting the agents waiting on you (click opens the one that has waited longest) next to a live count of running agents, ⌘K/Ctrl-K search over titles and branches, quick-reply buttons extracted from the agent's actual question (numbered or bulleted options, or an "A or B?" disjunction — at most 4, dropped entirely when any option looks unusable, plus an always-present "Something else…"), a reply field that parks your message while the agent runs and delivers it the moment the turn ends (a second message appends to the parked one — one turn, one message), and a folded tool feed showing live elapsed time and token count while the turn is in flight, then the turn's tool count, tokens and duration once it is done.

## [0.8.0] - 2026-07-16

### Added

- Dual review (`codesema review --dual`, or "Dual review" in the menu): two independent reviewers run in parallel on the same agent CLI — the reviewer (full narrative review) and the prosecutor (adversarial, findings only) — then a judge on the provider's mid-tier model (sonnet / gpt-5.5 / gemini-2.5-pro) adjudicates every finding: kept, merged as duplicate, or rejected with a reason. Security findings can never be rejected by the judge. Findings raised by both reviewers carry a `consensus` badge; the record stores the deliberation stats (`meta.dual`). If one reviewer fails the review finishes with the survivor; if the judge fails the union of both reviews is kept. Dual reviews always run from scratch (no incremental update).
- The live web UI shows both dual phases, at no extra token cost (everything derives from the two streams and the judge stream): a face-à-face of the two reviewers with live severity counters, a per-file consensus map where files lit by both lanes pulse as hot zones, then the deliberation with each judge decision resolving live (kept / merged / rejected with the reason).
- Deterministic grounding of the agent review against the diff, before display and archive (`groundReview` in `@codesema/contract` 0.3.0): findings on files absent from the diff are dropped, line anchors outside every hunk are removed, duplicate findings (same file, line and kind) merge into one with the highest severity, and an `approve` verdict with a surviving critical finding is escalated to `request_changes`. `codesema review` prints what was corrected.
- `impact_candidates` in the prep input and the review prompt: when the MR modifies or removes an exported declaration (TypeScript/JavaScript exports, Python top-level `def`/`class`), `codesema prep` lists where that symbol is used elsewhere in the repository (`git grep`, word-matched, capped and deduplicated) and which files import the changed files, so the agent can flag call sites the diff does not update. Zero new dependencies; the block is explicitly labeled as best-effort text matches, and the review instructions require the agent to treat it as leads to verify, never as facts.
- Reviewer coverage tracking: both reviewers report the diff files they examined (`files_reviewed` in `@codesema/contract` 0.3.0) and `codesema review` warns about any diff file a reviewer skipped (full reviews only; incremental updates are exempt).
- Deterministic cross-lane consensus: findings raised by both dual reviewers on the same file, line and kind merge before the judge runs — fewer decisions to pay for, and the consensus badge survives even a judge failure.
- Auto-sync, strictly opt-in: after a successful `codesema sync`, the CLI offers once to also push every future completed review automatically (`syncAutoPush` in the global config; workspace credentials alone never auto-push), and the `codesema config` menu toggles it anytime. Best-effort and never blocking: a sync failure or a diff carrying potential secrets keeps the review local and says so (secrets still require a manual `codesema sync --force`).
- One automatic retry when the agent output holds no parseable JSON review (lanes, judge and simple review), with a short corrective instruction; agent crashes and timeouts are never retried.
- A prompt evaluation bench under `packages/cli/eval/` (labeled bug fixtures + recall/noise report) to measure reviewer prompts before and after changes; development tool, not shipped.

### Changed

- Hardened reviewer prompts: mandatory file-by-file sweep with no early stop and no implicit findings cap, severity definitions by consequence, mandatory concrete failure scenario per finding, strict line anchoring (omit the line rather than guess), a pre-output self-check, and systematic follow-up of `impact_candidates` usages. The judge must cite the exact diff lines when rejecting a finding and shares the same severity scale.
- The review diff now carries 10 context lines per hunk (git default is 3), so reviewers judge changes against the enclosing code.
- A `praise`/`why` finding is always severity `info`: a mis-scored praise can no longer escalate the verdict or trip `--fail-on`.

- The agent prompt no longer carries prep plumbing: the absolute repository path, commit SHAs and internal metadata are stripped; the agent receives only the branch names, commit subjects, changed files, custom instructions and the diff.
- Commit subjects are truncated to 120 characters in the prep input, and the review instructions now state that commit messages are intent context only, never evidence.

### Security

- The review subprocess runs the known agent CLIs with tools switched off: `claude -p` gets `--tools "" --strict-mcp-config --setting-sources user` (no tools, no MCP servers, repo-level `.claude/` settings ignored) and `codex exec` gets `--sandbox read-only --ask-for-approval never` plus `AGENTS.md` loading disabled. Flags already present in the command win; the fix runner keeps its edit tools. Gemini has no CLI flag for this; its non-interactive mode already denies shell and write tools.
- Known agent CLIs are spawned with a minimal environment (`PATH`, `HOME`, locale, proxy and the provider's own variables): other credentials and tokens in your environment no longer reach the review subprocess. Custom agent commands inherit the full environment as before.
- Diff marker line parsing in `@codesema/contract` (`--- ` / `+++ ` paths) no longer uses a polynomially backtracking regex (CodeQL: polynomial ReDoS): a crafted diff line packed with tabs and a stray carriage return could stall `detectDiffSecrets` and `groundReview` for seconds. The tab suffix is now stripped with a linear `indexOf` scan.

- `codesema sync` scans the diff for material that looks like a committed secret (dotenv files, private keys, and AWS/GitHub/Slack/Google/Stripe/OpenAI/Anthropic credentials, on both added and removed lines) and refuses to upload it; pass `--force` to send anyway.
